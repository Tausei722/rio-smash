# 仕様書: 親子3代英語（専用ゲームモード）

## 概要・目的

もともと「カテゴリを選んで対戦」内の一群のカテゴリ（`親子3代英語シーン別辞書「◯◯」`）としてのみ存在していたコンテンツを、独立したゲームカードに昇格させた。ホーム画面で「2人対戦」の下に並び、対象カテゴリの単語だけで2人対戦の仕組みをそのまま使う。

ゲームの進行・スコアリング・画面構成は[spec-2players.md](./spec-2players.md)と完全に共通。本ドキュメントは「対象カテゴリの束ね方」「コンテンツのアクセス制御」「コンテンツ整理の未決事項」に絞る。

### サービスとしての前提（2026-08-29追記）

このモードは運営者が個人的に、特定アカウントのユーザーへコンテンツをプレゼントするための仕組み。運用フロー:

1. 対象ユーザーから「どんな英語が喋れるようになりたいか」の要望をもらう
2. 運営者がその要望に見合った問題（フレーズ）を作成し、専用カテゴリとして登録する（例: `親子3代英語シーン別辞書「ひび」さん専用`）
3. そのカテゴリは**要望を出した本人のアカウントにだけ**表示・出題される。他のユーザーには一切見えない

一方で、人物名の付いていないシーン別カテゴリ（`気をつけてほしい` 等）は特定個人向けではなく、**有料会員なら誰でも見られる共有コンテンツ**という別の性質を持つ。両者は現在同じ`category`列に混在しているが、公開範囲のルールは全く異なる（詳細は[個人限定配信の仕組み](#個人限定配信の仕組みコンテンツアクセス制御)）。

## スコープ

- やること: 該当カテゴリ群を1つのゲームカードとして提示、専用の単語プールでバトルを実行
- やること: 人物タグ型カテゴリ（個人プレゼント）を、割り当てられた本人のアカウント以外には一切見せない・出題しないアクセス制御
- やらないこと（今回未着手）: カテゴリの再編・重複コンテンツの統合・命名規則の統一（後述、未決事項）

## 業務ルール

- 対象カテゴリの判定は文字列前方一致: `category.startsWith('親子3代英語シーン別辞書')`（[App.tsx:644-647](../App.tsx#L644-L647), `OYAKO_PREFIX`）
- 出題ロジック・スコアリング・ターン制・10問制限は[spec-2players.md](./spec-2players.md#業務ルール)と同一（`startGame(oyakoCategories)`が内部で`category`一致フィルタをかけるだけ）
- **⚠️現状の実装は個人限定配信を一切考慮していない**: 今の`oyakoCategories`は前方一致した全カテゴリ（人物タグ型・シーンタグ型問わず）を無条件に束ねて全ユーザーに見せている。つまり`親子3代英語シーン別辞書「ひび」さん専用`は現時点で**全ユーザーから見え、出題される**（下記アクセス制御の実装前は仕様と実装が食い違っている状態）

## 個人限定配信の仕組み（コンテンツアクセス制御）

カテゴリを2種類に分けて扱う。

- **共有カテゴリ**（シーンタグ型など、人物名の付いていないもの）: 従来どおり`premium_categories`（[src/db/database.ts:37-45](../src/db/database.ts#L37-L45)）で有料/無料を判定。ログインユーザーなら誰でも対象（有料会員なら有料カテゴリも）
- **個人限定カテゴリ**（`「◯◯」さん専用`など）: 割り当てられた**特定の1アカウントにしか見えない**。有料/無料の概念とは別軸

判定方法は文字列パターン（`さん専用`等）に頼らず、**カテゴリ⇔アカウントの対応表**で管理する（どのカテゴリが個人限定でどのアカウント向けかを明示的にデータとして持つ）。命名規則に依存しないので、シーン名的なカテゴリを将来的に個人限定にすることもできる。

### 可視性ルール

あるカテゴリ`C`がユーザー`U`に見える条件:

1. `category_access`テーブルに`C`の行が**1件も無い** → 従来どおり「共有カテゴリ」として扱う（無料 or `premium_categories`と`U`の有料会員フラグで判定）
2. `category_access`テーブルに`C`の行が**1件以上ある** → 「個人限定カテゴリ」として扱い、`(category = C, user_id = U)`の行が存在する場合のみ見える。他のユーザーには一切表示・出題しない

この判定は`親子3代英語シーン別辞書`カテゴリに限らず、カテゴリ全般に適用できる汎用ルールとして設計する（他のカテゴリを将来個人限定化する場合にも流用できる）。

## データモデル

既存`words`テーブルの`category`列の値パターンで束ねる部分は変更なし（[App.tsx:645-647](../App.tsx#L645-L647)）。個人限定配信のために新規テーブルを1つ追加する。

```sql
create table category_access (
  category    text not null,
  user_id     uuid not null references auth.users(id) on delete cascade,
  created_at  timestamptz default now(),
  primary key (category, user_id)
);
```

- `category`: `words.category`と同じ文字列（例: `親子3代英語シーン別辞書「ひび」さん専用`）
- `user_id`: Supabase Authのユーザーid（`profiles.id`と同一値）
- 1カテゴリに複数ユーザーを紐付けることも可能な設計（将来「家族全員に共有」等が出た場合に対応できる）だが、現状の運用は1カテゴリ=1アカウント

取得関数（[src/db/database.ts](../src/db/database.ts)に追加、既存の`fetchPremiumCategories`と同パターン）:

```ts
// 個人限定カテゴリとして登録されている全カテゴリ名（誰が対象かは問わない）
export async function fetchRestrictedCategories(): Promise<Set<string>> { ... }

// 自分（userId）がアクセスできる個人限定カテゴリ名の一覧
export async function fetchMyAccessibleCategories(userId: string): Promise<string[]> { ... }
```

`App.tsx`側の`oyakoCategories`算出（[App.tsx:644-647](../App.tsx#L644-L647)）は、共有カテゴリ（従来ロジック）と、個人限定カテゴリのうち自分がアクセス権を持つものだけを合算する形に変更する（未実装、[未決事項](#未決事項)参照）。
